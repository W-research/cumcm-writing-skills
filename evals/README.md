# Evals

## 三种检查

- 离线测试：目录、链接、独立安装、可维护字段、数值与检查器失败控制。
- 模型输出：根据输入生成响应，再检查任务、答案和限定条件。
- 职责路由：包含含糊请求、非竞赛任务、其他竞赛以及宽泛Skill共装冲突。

## 本地命令

~~~sh
python -m unittest discover -s evals -p 'test_*.py' -v
python evals/check_outputs.py --responses evals/runs
python evals/check_freshness.py
~~~

这些检查只读本地内容，不调用付费模型。check_freshness默认警告；正式发版可加 --release。指纹不是“每改一个字就必须重跑模型”的贡献门槛，维护者可按变更影响选择相关用例。

## 生成模型输出

在仅暴露本插件五个Skill的独立进程中运行；先做目录探针，记录实际可见名称，不能只要求模型“忽略其他Skill”。关闭其他插件、用户/项目附加指令和记忆注入，保留运行所需的认证配置。探针未能确认隔离时应标记污染，而非计为纯插件结果。

正文评估采用 `harness_inline`：将选中Skill的完整入口和参考Markdown文本作为输入提供，不经过原生文件读取工具。这个模式衡量隔离后的指令效果；客户端按需读取、市场安装和文件工具可靠性属于另一层集成测试。两种结果不得混称。

- 路由只给名称/描述和 inputs/routing.json，输出每项的 skills 与 action（use、clarify、answer）。
- C01给题面整理及三节模板请求，读取重述Skill及适用参考。它与官方2020 C教学材料有意重合，只检查已知来源的结构与条件保留。
- C02使用新的质量检验题，答案未出现在教学参考中；覆盖分类口径、有限候选及新批次全部不可行。
- 另在同一环境仅加入math-modeling-paper的触发描述作冲突探针。结果单列，不能强行把同时触发记成专用Skill的成功。

维护者判断保存在cases.json。生成响应时不向模型提供该文件、检查器或已有答案。模型结果写入新的运行目录后再检查，公开前移除本机路径和敏感信息。

## 测试材料隔离

`test_fixture_isolation.py` 扫描整个 `skills/` 的文本文件。对cases.json标为 `isolated_content_regression` 的用例，从输入自动提取三位及以上数值和非整数小数，检查其是否被写进运行材料；另检查该用例声明的场景短语。小整数、整数百分比、版本号或哈希子串不作裸数字拦截，以免把通用示例和来源标识误判为泄漏。

每个inputs文件都需声明用途；共享官方来源的结构用例标为 `known_source_regression` 并说明原因，路由请求单独处理。新增内容用例应优先使用独立场景并声明关键短语。防泄漏检查能阻止具体数据和场景词回流，不证明语义上完全无重合；反复用于修订的C02仍是开发回归用例，不是从未使用过的留出集。

## 判定边界

关键数字只能作为必要条件。例如写了87.5%和82.5%，却把差异称为5%的相对提升，仍应失败；出现方案成本也不能掩盖第三问没有可行方案的事实。检查器之后仍需语义审阅。

摘要先按“正文外说明”标题，或关键词后的独立分隔线拆分。数值、240件独立测试集、候选范围与阈值等事实检查只读取论文正文；未完成验证等工作信息允许放正文外，既不强制添加，也不能用它替代必答结果。检查器同时拒绝正文中的防御性备注和无证据的显著性/推广主张。无可行方案属于直接答案，不能因为表述带“不”就删除。

含糊的“第一部分”“建模思路”应请求任务上下文；普通课程论文摘要不属于竞赛Skill。规则重叠时报告冲突，不擅自修改其他插件。

原生Word/MathType测试由独立手工记录支持，不计入文本生成评估。测试记录中的模型与入口版本只写实际取得的信息。
